### Phase 4 (new) — Purchasing
- **Suppliers** (`apps/api/src/modules/purchasing/application/suppliers/`): create/update/deactivate/list/get. Soft-delete only (`isActive` toggle) — deactivation is blocked while the supplier has any open (`DRAFT`/`APPROVED`/`PARTIALLY_RECEIVED`) purchase. Balance is never stored on the row; every read computes it fresh.
- **Purchase documents** (`application/purchases/`): `Purchase` + `PurchaseItem` with lifecycle `DRAFT → APPROVED → PARTIALLY_RECEIVED → RECEIVED`, or `→ CANCELLED` from any of `DRAFT`/`APPROVED`/`PARTIALLY_RECEIVED`. A `DRAFT` purchase's items are fully editable (replace-all-lines); once `APPROVED` the document is immutable except through approve/cancel/receive/return. Approval is a **deliberate separate step from receiving** — it commits the business to the order but has zero inventory/ledger effect of its own, which is what makes partial and multiple receiving operations against the same purchase well-defined.
- **Receiving** (`application/receiving/receive-purchase.use-case.ts`) — the ONLY place in Purchasing that touches inventory, and it does so exclusively through `InventoryEngineService.applyMovement` (movementType `PURCHASE`), never a direct write to `stock_balances`/`stock_movements`. One call to `POST /purchasing/purchases/:id/receive`:
  1. Locks the `Purchase` document row (`SELECT ... FOR UPDATE`) — the document-level lock target, distinct from and in addition to the Inventory Engine's own `StockBalance` lock.
  2. Validates every line against `quantityOrdered - quantityReceived` (over-receiving rejected with `CONFLICT`), both within one call and cumulatively across prior receipts.
  3. Creates a `PurchaseReceipt` + `PurchaseReceiptItem` row per line (the event record, with the exact `unitCost` this batch is costed at, copied from `PurchaseItem.unitCost`).
  4. Calls the Inventory Engine per line with that cost as `unitCostOverride`, so `StockMovement.unitCostAtMovement` and the resulting WAC blend are computed by the engine's existing, already-reviewed math — nothing reimplemented.
  5. Increments `PurchaseItem.quantityReceived` and posts a `SupplierTransaction(PURCHASE, +value)` — the payable increase and the inventory increase for the same goods land in the exact same DB transaction.
  6. Recomputes and sets `Purchase.status` (`PARTIALLY_RECEIVED` or `RECEIVED`).
  All of the above is one atomic transaction — any failure anywhere in it rolls back every part, verified explicitly by test (see Tests and Results).
- **Purchase Returns** (`application/returns/create-purchase-return.use-case.ts`) — a single-step atomic action (not a draft/confirm workflow): reverses inventory via `InventoryEngineService.applyMovement` (movementType `PURCHASE_RETURN`, a negative delta) and posts a supplier credit, in one transaction. Bounded by `quantityReceived - quantityReturned` per line (never more than was actually received), and **deliberately decoupled from `Purchase.status`** — a purchase cancelled after a partial receipt can still have that received portion returned, since the return's validity is a property of the line, not the document's terminal state. The engine's existing "a decrease always costs out at the current average cost, `unitCostOverride` ignored" rule applies with zero special-casing; the supplier credit uses the *original* purchase cost instead (a different, legitimate concern — what we're owed back, not what the stock is worth today).
- **Payments** (`application/payments/create-purchase-payment.use-case.ts`) — records a `PurchasePayment` against a purchase and posts a `SupplierTransaction(PAYMENT, -amount)`. Deliberately **not** wired to any `FinancialAccount`/`JournalEntry` — that is Phase 6 (Accounting Engine) scope entirely; this is the clean, additive boundary that phase will read from later, not a parallel or fake accounting system.
- **Supplier balance** is `SUM(SupplierTransaction.amount)`, computed on every read (`domain/supplier-balance.ts`) — never a stored, directly-editable column, mirroring the Phase 3 `StockBalance`-is-a-cache-of-the-ledger principle (here there isn't even a cache, since write volume doesn't warrant one).
- **Idempotent receiving**: `PurchaseReceipt.idempotencyKey` (optional, unique per business when present — Postgres treats multiple `NULL`s as non-conflicting, so it's opt-in per request, same pattern as Phase 1's `RefreshToken`). A retried request with the same key returns the original receipt rather than double-applying inventory.
- **Document numbers** (`PO-XXXXXXXX`, `GRN-XXXXXXXX`, `PRET-XXXXXXXX`) are derived deterministically from each row's own client-generated UUID (`domain/document-number.ts`), never a shared counter/sequence — no two documents can ever collide, and no extra locking infrastructure was needed to guarantee that under concurrent creation.

## Architecture Decisions
Everything from Phase 0-3 stands unchanged. New Phase 4 decisions, each explained:

- **Purchasing is a consumer of `InventoryEngineService`, never a parallel inventory system.** `ReceivePurchaseUseCase` and `CreatePurchaseReturnUseCase` are the only two places in this module that call the engine, and both call `applyMovement` exactly as every Phase 3 use case does — no new locking, costing, or persistence logic was written for inventory. This was verified, not just intended: every receiving/return e2e test asserts on real `StockMovement`/`StockBalance` rows with `movementType PURCHASE`/`PURCHASE_RETURN`.
- **Document, Receiving, Inventory Movement, and Payment are four separate use-case groups, not one service.** `application/purchases/` (document CRUD + approve/cancel), `application/receiving/` (the only inventory-touching code), `application/returns/`, and `application/payments/` are separate folders with separate injectable use-cases, each with a single reason to change — directly satisfying the "no God Service" instruction.
- **The Purchase document row is locked (`SELECT ... FOR UPDATE`) as the concurrency-control target for the over-receiving/over-returning invariant** (`domain/lock-purchase.ts`), deliberately separate from the Inventory Engine's own `StockBalance` lock. The Engine's lock protects stock correctness for a `(warehouse, variant)` pair; it says nothing about "has this specific PO line already received its full ordered quantity." Locking the Purchase row (rather than each `PurchaseItem` row individually) is sufficient and simpler, because every mutation to any of that purchase's items — receiving, returning, editing while still `DRAFT` — happens only while holding this lock; two concurrent receive/return calls against the *same* purchase therefore serialize on it, proven directly by a real-concurrency e2e test (see Concurrency Review).
- **Approval is a separate step from receiving**, a deliberate refinement beyond Phase 0's one-line description of Purchasing, required by this phase's explicit partial/multiple-receiving and over-receiving-prevention rules — a `DRAFT` purchase is still fully editable and has never touched inventory; only once `APPROVED` does it become an immutable commitment that receiving can be checked against.
- **`SupplierTransaction(PURCHASE)` is posted at *receiving* time, not approval time.** This is what guarantees the payable increase and the inventory increase for the same goods are always in the same DB transaction — approval has no financial effect at all, matching the real-world fact that money/inventory only actually move when goods physically arrive.
- **Supplier balance is `SUM(SupplierTransaction.amount)`, never a stored column** — the same "ledger is the only truth, balance is derived" principle as `StockBalance`, extended to a domain that doesn't even need a cache at Phase 4's write volume. `SupplierTransaction` is append-only at the DB-privilege level (SELECT+INSERT only for `erp_app`), exactly like `stock_movements`.
- **Purchase Return is single-step and status-independent**, not a draft/confirm workflow — bounded purely by `quantityReceived - quantityReturned` per line, so a return remains valid even against a `CANCELLED` purchase document, as long as the specific line still has un-returned received quantity. This correctly separates "is there something to give back" (a line-level fact) from "what is this document's overall lifecycle state" (a header-level concern).
- **Document numbers are derived from a client-generated UUID, not a shared sequence.** `randomUUID()` is generated in the use case before the `create()` call, and the human-readable number (`PO-<first 8 hex chars>`) is computed from it in the *same* insert — avoiding both a follow-up `UPDATE` (which several Phase 4 tables deliberately don't grant, being append-only) and any shared-counter contention between concurrent purchase/receipt/return creations.
- **`purchase_items` needed a narrow, deliberate exception to the "no DELETE" posture**, added in its own follow-up migration (`20260828191700_purchase_items_delete_grant`) rather than folded into the original grants migration — mirroring the Phase 3 precedent of the `lot_fk_restrict` fix being its own migration. Editing a still-`DRAFT` purchase's line items replaces the whole set, which needs to delete lines no longer present. This is safe specifically because `purchase_receipt_items.purchase_item_id` and `purchase_return_items.purchase_item_id` both carry `ON DELETE RESTRICT` foreign keys — Postgres itself refuses the delete of any `PurchaseItem` that has ever been received or returned against, regardless of what application code does, so only a line that only ever existed within an (application-enforced) `DRAFT` purchase can actually be deleted.
- **`branchId` is never accepted as purchase-creation input** — only `warehouseId` is, and `branchId` is always derived server-side from `warehouse.branchId`, exactly matching the established Phase 3 convention (`opening-stock`/`receive-stock`/`consume-stock`/`adjust-stock` all do the same). This structurally eliminates an entire class of bug where a caller could supply a `branchId`/`warehouseId` pair that don't actually belong together.
- **A Purchase targets exactly one `warehouseId`** (set at creation, inherited by every receipt/return against it) rather than letting receiving specify an arbitrary warehouse per call — a deliberate scope decision (see Pending Features) that keeps the receiving invariant simple and matches how a real purchase order is issued against one delivery location.

## Migrations
1. `20260828191031_purchasing_schema` — the 9 tables/3 enums above, plus hand-written `CHECK` constraints: non-negative `payment_terms_days` on `suppliers`; non-zero `amount` on `supplier_transactions`; non-negative subtotal/tax/discount/total on `purchases`; positive `quantity_ordered`, non-negative `quantity_received`/`quantity_returned`, **`quantity_received <= quantity_ordered`**, **`quantity_returned <= quantity_received`**, non-negative cost/tax/discount/line-total on `purchase_items`; positive quantity + non-negative cost on `purchase_receipt_items`/`purchase_return_items`; positive `amount` on `purchase_payments`. 4. `20260828191700_purchase_items_delete_grant` — a narrow, explained follow-up (see Architecture Decisions) granting DELETE specifically on `purchase_items`, safe only because of the `ON DELETE RESTRICT` FKs from `purchase_receipt_items`/`purchase_return_items` proven in the review below.

Caught by literally attempting to delete a business with receipt/return-item rows as the migration/owner role and observing a real `violates foreign key constraint` error — not by re-reading the schema file. **Not reachable by the running application** (`erp_app` has no DELETE grant on `businesses` at all, same as every prior phase), so this was a latent migration-hygiene inconsistency, not a security, tenant-isolation, or correctness defect. Fixed and reverified live on both databases.

## Business Logic Review
- Every purchasing use case validates its references (warehouse/supplier/variant belong to the caller's tenant, supplier is active) before writing anything, returning 404/422 rather than silently creating cross-tenant or invalid data — same discipline as Phases 1-3.
- Every quantity/cost value is a `Prisma.Decimal` throughout, matching Phase 3's no-floating-point-near-money discipline.
- The three places this phase does something meaningfully more sophisticated than "call an existing use case" — the Purchase-row lock for over-receiving/over-returning, the idempotency-key dedup on receiving, and the atomic multi-line receive/return — are each covered by a test that specifically targets that sophistication (a real concurrency race, a real duplicate request, a real multi-line partial failure) rather than only the happy path.
- Cancellation is scoped correctly: it only closes out *unreceived* remaining quantity and never touches already-received inventory or already-posted ledger entries — verified by the "return after cancel" test, which would be nonsensical if cancellation had tried to reverse history instead of just closing the future.

## Inventory Integration Review
Direct evidence that Purchasing is a real, atomic consumer of the Inventory Engine and not a parallel system:
1. **No new source of inventory truth was created.** Grep-verified: the only two calls to `InventoryEngineService.applyMovement` in the entire `purchasing` module are in `ReceivePurchaseUseCase` and `CreatePurchaseReturnUseCase`; nowhere in Purchasing is `stock_balances`/`stock_movements` written directly.
2. **`unitCostAtMovement` is preserved exactly as designed in Phase 3** — a receipt's `PurchaseReceiptItem.unitCost` (copied from `PurchaseItem.unitCost` at receiving time, never retroactively changed) is passed as `unitCostOverride`, and the resulting `StockMovement.unitCostAtMovement` is verified byte-for-byte in tests. A return passes no cost override at all, deliberately relying on the engine's existing "decrease always costs at the current average" rule — zero special-casing, verified by the return test not asserting any particular cost on the reversing movement beyond what the engine itself would produce.
3. **Every receiving/return operation is one atomic DB transaction** spanning the `PurchaseReceipt`/`PurchaseReturn` event record, the Inventory Engine call(s), the `PurchaseItem` running-total update, and the `SupplierTransaction` ledger write — proven directly by the atomicity test (one bad line in a multi-line receive rolls back the good line too: zero balance, zero movements, zero ledger rows, unchanged purchase status).
4. **No historical `StockMovement` is ever modified or deleted by a return** — proven by re-reading the original `PURCHASE` movement byte-for-byte after a `PURCHASE_RETURN` was posted and confirming it is completely unchanged; the reversal is exclusively a new, opposite movement.
5. **Bundle consumption, transfers, stock counts, and every other Phase 3 capability are untouched** — Purchasing added zero lines to `inventory-engine.service.ts` or any Phase 3 use case; the full Phase 3 regression suite (34 tests) still passes unmodified.

## Concurrency Review
**Updated during the Phase 4 release-gate review** — the original report covered only receive/receive races; two more real-concurrency tests were added and run to close verification gaps the review specifically asked about (return/return races, and TRUE simultaneous idempotency-key collisions rather than only sequential retries). All four fire genuinely concurrent HTTP requests (`Promise.all` against the live, already-running NestJS app, real PostgreSQL round-trips for each):
1. **Two concurrent receive requests for the same Purchase, each asking for 6 of a 10-unit outstanding line (12 total requested, only 10 available)**: exactly 1 succeeds (201), exactly 1 is rejected (409 `CONFLICT`), `PurchaseItem.quantityReceived` ends at exactly `6` (never `12`), the `StockBalance` ends at exactly `6`, and exactly one `PURCHASE` `StockMovement` was ever recorded — the rejected request left no trace anywhere.
2. **Two concurrent receive requests that together exactly exhaust the outstanding quantity (5 + 5 of 10)**: both succeed with no lost update — `quantityReceived` ends at exactly `10`, the purchase transitions to `RECEIVED`, and both `StockMovement` rows exist (not one silently overwriting the other).
3. **Two concurrent return requests for the same Purchase, each asking to return 6 of a 10-unit received line (12 total requested, only 10 returnable)**: exactly 1 succeeds, exactly 1 is rejected, `quantityReturned` ends at exactly `6` (never `12`), and exactly one `PURCHASE_RETURN` `StockMovement` was ever recorded — proving the same Purchase-row lock correctly serializes returns, not just receives.
4. **Two TRULY simultaneous receive requests with the identical `idempotencyKey`** (neither has committed when the second starts, as opposed to a sequential retry-after-commit): exactly 1 succeeds (201), the other fails (mapped to an error, not a silent duplicate), exactly one `PURCHASE` `StockMovement` was ever recorded, and exactly one `PurchaseReceipt` row exists for that key.

Mechanism: `lockPurchase` (`domain/lock-purchase.ts`) takes `SELECT ... FOR UPDATE` on the `Purchase` row before either use case reads or writes anything related to it. Postgres blocks the second transaction's `FOR UPDATE` until the first commits or rolls back, so the second transaction always recomputes "how much of this line is still outstanding/returnable" against the first one's already-applied change — never a stale read. This is the identical mechanism/guarantee Phase 3 uses for `StockBalance`, applied one layer up at the document level. Because both `ReceivePurchaseUseCase` and `CreatePurchaseReturnUseCase` take this SAME lock before touching a Purchase's items, a receive and a return racing on the *same* purchase are also fully serialized against each other, not just receive-vs-receive or return-vs-return — this was verified by code inspection (both call `lockPurchase` first, unconditionally) rather than a dedicated mixed-operation test.

**Lock-ordering / deadlock analysis (requested explicitly in the release-gate review), stated precisely rather than asserted as blanket-safe:**
- Within Purchasing, lock acquisition order is always Purchase-row → StockBalance-row(s), never the reverse (`InventoryEngineService` has no knowledge of `purchases` at all and never locks it). No code path acquires these two lock types in the opposite order, so **no deadlock is possible between the Purchase-row lock and any StockBalance lock**.
- Two concurrent operations on the **same** Purchase fully serialize on its row lock *before* either one reaches any `StockBalance` lock — so they can never race on `StockBalance` acquisition order at all.
- Two concurrent operations on **different** Purchases that happen to touch the same `(warehouse, variant)` simply serialize on that shared `StockBalance` row, exactly like two concurrent sales would in Phase 3 — not a deadlock, since neither transaction ever waits on the other's Purchase-row lock.
- **One real, disclosed exposure**: a multi-line receive (or return) call processes `input.items` in client-supplied order with no canonical sort before acquiring each line's `StockBalance` lock. Two concurrent calls against **two different Purchases** that share **more than one** common variant, requested in a different relative order between the two calls, form the classic lock-order-inversion pattern (TxA holds X, wants Y; TxB holds Y, wants X) and could theoretically deadlock. Postgres's own deadlock detector (`deadlock_timeout`, default 1s) always resolves this safely by aborting one transaction with a `deadlock_detected` (55P03) error rather than hanging — so **no data corruption or hang is possible**, but the aborted request currently surfaces as a generic 500 rather than a domain-mapped, automatically-retried error. This is not a Phase 4 regression: Phase 3's multi-component bundle consumption has the identical, pre-existing, undisclosed exposure (also unsorted). Not reproduced under a real deadlock in testing (doing so reliably requires precise inter-transaction timing control the harness doesn't currently have); the analysis above is by code inspection, stated honestly as such. Recorded as non-blocking technical debt below, with a concrete fix (sort lock-acquisition order by `variantId` before each engine call) that would apply equally to Phase 3's bundle consumption.

## Known Issues / Technical Debt
Phase 1-3's lists stand unchanged. New from Phase 4 (items 23-25 found specifically during the release-gate review, not at original implementation time):

18. **No landed cost / additional receiving costs (freight, customs, handling)** — a receipt's inventory cost is exactly `PurchaseItem.unitCost`; no mechanism exists yet to allocate extra costs across received lines. Not required by this phase's spec and would meaningfully complicate the WAC integration without a corresponding tested requirement.
19. **A Purchase is pinned to one `warehouseId` for its whole lifecycle** — receiving/returning always target that same warehouse. Splitting a single PO's receiving across multiple warehouses was judged out of scope (see Architecture Decisions); if ever needed, the natural extension is per-receipt warehouse selection with validation that it belongs to the same business.
20. **No supplier-specific product pricing/catalog** — `PurchaseItem.unitCost` is entered manually per purchase; there's no "last purchase price" or supplier price list lookup to pre-fill it. Straightforward additive read-only convenience if wanted later, not a correctness requirement.
21. **`PurchasePayment` has no void/reversal endpoint** — a mis-recorded payment currently has no built-in correction path beyond a manual offsetting `SupplierTransaction` (not exposed via API). Deferred since Phase 4's spec required recording payments as a Phase 6 integration boundary, not a full payments-correction workflow.
22. **No Accounting Engine integration yet** — `PurchasePayment`/`SupplierTransaction` are structured as the integration boundary (immutable, complete records of what/when/how/against-which-purchase) but are not posted to any `FinancialAccount`/`JournalEntry`, since that engine doesn't exist until Phase 6, per explicit instruction not to build a parallel/fake accounting system early.
23. **`PurchaseReturn` has no `idempotencyKey`, unlike `PurchaseReceipt`** — a genuine, disclosed asymmetry found during the release-gate review. A network-retried duplicate return request is NOT deduplicated the way a retried receive is: it would create a second, independently-valid `PurchaseReturn` (each individually bounded by `quantityReturned <= quantityReceived`, so it can never over-return beyond what was physically received, and every row stays fully auditable) — but two real, distinct return+credit events would be recorded where the caller likely intended one. Not data corruption, but a real gap against the instruction to cover "duplicate requests/idempotency where applicable" for Purchasing broadly, not just receiving. Recommended fix: add `idempotencyKey` to `PurchaseReturn` mirroring `PurchaseReceipt` exactly (same nullable-unique-per-business pattern) — small, additive, no redesign needed.
24. **Multi-line receive/return lock-ordering deadlock exposure** — see the Concurrency Review's dedicated analysis. Theoretical, Postgres-detected-and-safely-aborted (never a hang or corruption), pre-existing in the same unsorted form in Phase 3's bundle consumption, and not reproduced under a real race in testing. Recommended fix: sort each call's variant-lock acquisitions by `variantId` before invoking the Inventory Engine, in both this phase's receive/return loops and Phase 3's bundle consumption loop.
25. **No cost-visibility gating on Purchasing reads** — unlike `products.view_cost` gating cost fields in Catalog/Inventory responses, `GetPurchaseUseCase`/`ListPurchasesUseCase` return `unitCost`/`subtotal`/`totalAmount` unconditionally to anyone holding `purchases.view`. Assessed as an intentional, reasonable difference rather than a gap — a Purchase document's entire substance *is* cost information, unlike a Product record which legitimately needs broad read access (POS, catalog browsing) independent of cost visibility — and no current role template (`CASHIER`/`SALES_EMPLOYEE`) is granted `purchases.view` at all. Flagged here for explicit visibility rather than silently assumed correct, since it wasn't discussed in the original Phase 4 spec.
